# 문서 작성 가이드 — 독자부터 정한다

> **읽는 이:** Claude. 문서를 쓰기 직전에 읽는다. 사용자는 이 가이드가 맞는지 검토할 때 읽는다.
> **상태:** v0.2 (2026-11-23). 라운드 1 피드백 반영. 바뀐 내역은 [feedback-log.md](feedback-log.md), 피드백 원문은 [feedback/](feedback/).
> **함께 보기:** 독자 목록 [personas.md](personas.md) · 독자별 예시 [examples/](examples/)

---

## 0. 이 가이드가 고치려는 것

사용자 지적 (2026-11-23): Claude가 쓰는 문서는 **목적에 맞는 작성법**과 **누가, 무엇을 하려고 읽는지**에 대한 고려가 약하다.

Claude의 자가 진단 — 실제로 자주 하는 실수:

| 실수 | 결과 |
| --- | --- |
| 내가 일한 순서대로 쓴다 | 독자는 결론을 찾느라 끝까지 읽어야 한다 |
| 모든 독자에게 같은 깊이로 쓴다 | 채용 담당자용 카드에 클래스 이름이, 면접관용 글에 "열심히 했다"가 들어간다 |
| 파일명·내부 용어를 풀지 않고 쓴다 | 그 프로젝트를 모르는 사람은 읽을 수 없다 |
| 다음 행동이 없다 | 읽고 나서 무엇을 하라는 건지 모른다 |
| 사실 · 추측 · 확인 필요를 섞는다 | 포트폴리오에서 과장이나 거짓이 된다 |
| 빼지 못한다 | 아는 것을 다 쓰고, 중요한 한 줄이 묻힌다 |

## 0-1. 가장 먼저: 사람에게 쓰는 문서는 사용자의 글이다

> 사용자 피드백 (라운드 1, 원문): "항상 사람에게 쓰는 '모든' 문서를 쓸 때는 '사용자'가 쓰는걸 너가 대필해주는 입장과 같다는걸 명심해."

사람이 읽는 문서(포트폴리오, 프로젝트 문서, 멘토에게 보내는 질문, 팀원용 안내 등)는 **Claude가 사용자 대신 쓰는 글**이다. 읽는 사람은 사용자가 썼다고 생각하고 읽는다. 그래서 아래를 지킨다.

| 지킬 것 | 하지 않을 것 (라운드 1에서 실제로 지적받은 것) |
| --- | --- |
| 사용자의 목소리, 1인칭("저는", "제가")으로 쓴다 | AI 입장의 말: "~만 알려 주시면 됩니다"처럼 답의 형식을 지시하는 말 |
| **~습니다** 체로 쓴다 (사용자가 따로 정하지 않으면) | "~했다. ~봤다. ~었다."처럼 끊기는 보고서체 |
| 문장을 **이어지게** 쓴다. "그래서", "그런데", "~해 보니", "~때문에"로 앞뒤 관계가 보이게 | 사실을 한 문장씩 툭툭 늘어놓기. 사람이 쓴 것 같지 않고 재미가 없다 |
| 본문에는 **내용만** 둔다 | 문장의 역할을 알려 주는 라벨: `**질문:**`, `**맥락:**`, `**기준:**`, `[확인 필요: …]` |
| 처음 읽는 사람도 알아듣게 풀어 쓴다 | "A → B" 같은 화살표 요약 제목. 맥락을 아는 나만 알아본다 |
| 크기에 맞게 쓴다. 작은 문제는 작게 | 현업자가 보기에 별것 아닌 문제를 큰 발견처럼 쓰기 |

**모르는 사실은 어떻게 하나:** 본문에 빈칸 표시를 남기지 않는다. 그 사실이 없어도 글이 되면 빼고 쓰고, 꼭 필요하면 쓰기 전에 사용자에게 묻는다. 빠진 것 목록은 본문 밖(대화, 또는 예시 문서의 작성 메모)에 둔다.

**적용 범위 (Claude의 해석, 확인 필요):** 이 규칙은 "남에게 보여 줄 완성 글"에 적용한다. devlog · 결정 기록 · 재료집 같은 작업 기록과 AI가 읽는 문서(CLAUDE.md, 인수인계, 작업 지시)에서는 라벨과 `[확인 필요]`를 계속 쓴다. 사용자가 다르게 정하면 고친다.

## 1. 쓰기 전에: 독자 카드

어떤 문서든 쓰기 전에 아래 다섯 줄을 먼저 정한다. 정하지 못하면 사용자에게 묻는다.

```
독자:        누구인가 (personas.md의 ID, 또는 구체적인 사람)
읽는 목적:   읽고 나서 무엇을 판단하거나 하는가
읽는 상황:   언제 · 어디서 · 얼마나 시간을 쓰는가 (훑기 / 정독 / 찾기 / 따라 하기)
아는 것:     이미 아는 것과 모르는 것 (용어, 프로젝트 맥락)
성공 기준:   독자가 ___ 을 할 수 있으면 이 문서는 성공이다
```

- 독자가 둘 이상이면 **주 독자 하나**를 정한다. 나머지는 링크로 보낸다.
- 포트폴리오 · 면접 · 외부 공개용 문서는 초안을 줄 때 **독자 카드를 함께 보여주고** 사용자에게 확인받는다. 독자를 잘못 잡으면 문장을 다듬어도 소용없기 때문이다.
- 내부 기록(devlog, 결정 기록)은 독자가 정해져 있으므로 카드를 보여주지 않아도 된다.

## 2. 독자 카드가 정하는 다섯 가지

| 무엇 | 묻는 질문 | 독자에 따라 |
| --- | --- | --- |
| **순서** | 독자가 가장 먼저 알고 싶은 것은? | 판단하는 독자 → 결론 먼저. 따라 하는 독자 → 단계 순서. AI → 조건과 행동 |
| **깊이** | 무엇을 뺄까? | **빼는 목록을 먼저 정한다.** "이 문장이 없으면 독자가 잃는 것이 있나?" 없으면 뺀다 |
| **어휘** | 독자의 말은? | 비개발자 → 경험 · 효과의 말. 개발자 → 정확한 API 이름과 버전. AI → 경로와 이름을 글자 그대로 |
| **모양** | 어떻게 읽히나? | 훑는 독자 → 표 · 굵은 첫 문장 · 이미지. 정독 → 문단과 근거. 따라 하기 → 번호 단계와 확인 신호. 찾기 → 제목만 봐도 위치를 알게 |
| **다음 행동** | 읽은 뒤 무엇을 하나? | 끝에 한 줄로 둔다. 링크, 질문, 실행할 명령 등 |

## 3. 사람 독자와 AI 독자는 다르게 쓴다

| | 사람 | AI (Claude 새 세션, 서브에이전트) |
| --- | --- | --- |
| 기억 | 대략 기억한다. 요약을 반복해도 된다 | 매번 백지다. 문서에 없으면 모른다 |
| 읽는 법 | 훑고 건너뛴다. 첫 문장 · 표 · 그림이 중요하다 | 전부 읽지만 **글자 그대로** 따른다. 과하게 적용하기도 한다 |
| 설득 | 동기와 이야기가 있어야 움직인다 | 이야기가 필요 없다. **조건 → 행동** 형태가 가장 잘 지켜진다 |
| 모호함 | "적당히"를 상황에 맞게 해석한다 | "적당히"를 해석하지 못한다. 수치 · 예시 · 경계 사례로 쓴다 |
| 이유 | 궁금하면 묻는다 | 물을 수 없다. 규칙마다 **왜**를 한 줄 붙여야 처음 보는 상황에도 맞게 판단한다 |
| 충돌 | 상식으로 푼다 | 규칙끼리 부딪히면 무엇이 먼저인지 **문서에 적혀 있어야** 한다 |
| 오래된 정보 | 이상하면 알아챈다 | 그대로 믿는다. 날짜를 적고, 바뀌면 지운다 |
| 길이 | 길면 안 읽는다 | 길면 읽기는 하지만 중요한 규칙이 묻힌다. 핵심을 위에, 세부는 링크로 |

AI용 문서를 쓸 때 독자는 **"능력 있는 동료인데 이 프로젝트를 오늘 처음 본 사람"** 으로 생각한다.

## 4. 문서 종류별 작성법

| 문서 | 주 독자 | 독자의 목적 | 뼈대 | 흔한 실패 |
| --- | --- | --- | --- | --- |
| 포트폴리오 요약 카드 | H1 채용 담당자 | 30초 안에 "더 볼까" 판단 | 완성된 결과물 → 직무에 맞는 기술 → 내가 직접 만든 것 → 일하는 방식 | 기능 하나의 뒷이야기를 앞세우기 (라운드 1), 기술 이름 나열 |
| 프로젝트 문서의 고민과 선택 | H2 기술 면접관 | 이 사람의 판단력과 이해를 검증 | 문제 → 대안 2개 이상 → 선택과 이유 → 결과. 이어지는 글로 | 작은 문제 과장, 화살표 요약, 보고서체 (라운드 1) |
| 면접 준비 카드 | H3 미래의 나 | 질문에 바로 답할 재료 | 질문 → 한 문장 답 → 근거 위치 → 꼬리 질문 | 긴 설명, 근거 없음 |
| 결정 기록 | H3 미래의 나 · A1 Claude | 왜 이렇게 됐는지 찾기 | 문제 → 선택지 → 결정 · 결정한 사람 → 이유 → 상태 | 이유 없이 결론만, 누가 정했는지 없음 |
| 문제 해결 기록 | H3 · H2 | 재발 방지, 디버깅 과정 보여주기 | 증상 → 세운 가설 → 확인한 방법 → 원인 → 해결 → 배운 것 | 해결만 쓰고 추적 과정이 없음 |
| 사용 안내(how-to) | H5 팀원 · 다음 작업자 | 화면 옆에 띄우고 따라 하기 | 전제 → 번호 단계 + **단계마다 스크린샷** → 확인 신호 → 안 될 때 | 글로만 설명 (라운드 1), 성공 확인 방법이 없음 |
| 피드백 요청 | H4 강사 · 멘토 | 5분 안에 핵심 조언 | 묻고 싶은 것을 첫 문단에 → 상황 → 해 본 것 → 정중한 부탁. 라벨 없이 편지처럼 | `질문:` 같은 라벨, 답의 형식을 지시하는 AI 말투 (라운드 1) |
| 인수인계 · 기억 메모 | A1 Claude 새 세션 | 이어서 일하기 | 현재 상태 → 다음 할 일 → 지킬 규칙 → 주의 | 이야기체, 날짜 없음 |
| 작업 지시(브리프) | A2 서브에이전트 | 좁은 작업을 정확히 | 목표 → 범위 → 이미 확인한 것 → 결과 형식 | 내 가설을 답으로 심음, 범위가 열려 있음 |

예시는 [examples/](examples/)에 있다. **같은 사실을 독자만 바꿔 쓴 예시**(E1~E4)를 먼저 보면 차이가 잘 보인다.

## 5. 공통 문장 규칙

1. **첫 문장에 결론.** 제목 아래 첫 줄만 읽어도 핵심을 안다.
2. **한 문장에 정보 하나.**
3. **지어내지 않는다.** 작업 기록 · AI용 문서에서는 추측을 "(추측)", 근거 없는 것을 `[확인 필요: 무엇]`으로 표시한다. 사람에게 보여 줄 완성 글에서는 표시 대신 **빼거나 사용자에게 묻는다** (0-1).
4. **누가 했는지 쓴다.** 사람이 결정 · 작성 · 디버깅한 것과 AI가 한 것을 나눈다. 포트폴리오에서는 이것이 곧 평가 대상이다.
5. **숫자에는 단위와 출처.** "약 16 m/s (질량 0.31 기준 계산)".
6. **독자가 모르는 고유명사는 처음 한 번 풀거나 뺀다.** 비개발자에게 `IXRAimAssist`는 빼는 것이 맞다.

## 7. 이 가이드를 고치는 법

사용자 피드백을 받으면:
1. [feedback-log.md](feedback-log.md)에 피드백 원문 요약과 날짜를 적는다.
2. 이 가이드의 해당 절을 고치고, 맨 위 버전을 올린다.
3. 영향을 받는 예시와 [personas.md](personas.md)를 함께 고친다.
